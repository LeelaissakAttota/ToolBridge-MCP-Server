# Project Rules

These rules apply to all ToolBridge work. They protect the small, verified foundation while the system grows.

## 1. Source of truth

- Working code and tests define implemented behavior.
- `PROJECT_STATUS.md` is the concise current-state dashboard and must be updated when its tracked fields change.
- `ARCHITECTURE.md` distinguishes current architecture from target architecture.
- `TASKS.md` is the execution checklist; `ROADMAP.md` describes phase outcomes.
- Planned functionality must never be described as available.
- Update relevant documentation in the same change as behavior, interfaces, configuration, or operations.

## 2. Scope and approval

- Phases 1 through 4 are implemented; Phase 4 awaits project-owner acceptance.
- Do not begin Phase 5 implementation until the project owner accepts Phase 4 and approves an exact scope.
- Keep each change limited to an approved task with explicit acceptance criteria.
- Do not add speculative dependencies, services, provider SDKs, or infrastructure.
- Application code must not be changed by documentation-only tasks.

## 3. Engineering rules

- Support Python 3.12 unless a recorded decision changes the baseline.
- Preserve the single-process FastAPI/FastMCP foundation until an architectural decision supersedes it.
- Put runtime configuration in typed settings; never hard-code secrets or environment-specific credentials.
- Add type hints to public functions and meaningful docstrings to modules and public interfaces.
- Keep MCP tools small: validate input, delegate domain work, and return stable structured results.
- Do not couple core logic directly to a vendor SDK. Providers must sit behind project-owned interfaces.
- Prefer clear code and explicit failure modes over premature abstraction.

## 4. Quality gates

Before a change is considered complete:

1. The requested behavior is implemented and scoped.
2. Relevant automated tests pass.
3. Dependency integrity passes with `python -m pip check` when dependencies change.
4. No credentials, tokens, personal data, generated caches, or virtual environments are included.
5. User-facing behavior and operational changes are documented.
6. Security and error-handling implications have been reviewed.

## 5. Compatibility and interfaces

- Treat MCP tool names, input schemas, output shapes, HTTP paths, environment variables, and persisted formats as interfaces.
- Avoid breaking interfaces. If unavoidable, document migration steps and record the decision.
- Use explicit versioning for externally consumed interfaces once clients depend on them.
- Keep `/health` cheap and independent of optional external providers; add a separate readiness check when provider dependencies exist.

## 6. Dependencies

- Add a dependency only when it directly supports approved implementation.
- Pin direct dependencies in `requirements.txt` and test upgrades deliberately.
- Prefer maintained libraries with clear licensing and security practices.
- Remove unused dependencies promptly.

## 7. Security and privacy

- Follow `SECURITY_GUIDELINES.md` for every tool, provider, deployment, and logging change.
- Grant tools and providers the minimum permissions necessary.
- Validate all external input and bound resource usage.
- Never log secrets or full sensitive payloads.
- Do not enable public network exposure before authentication, authorization, rate limiting, and deployment hardening are implemented.

## 8. Repository hygiene

- Follow `GIT_WORKFLOW.md` for branches, commits, and reviews.
- Do not commit `.env`, `.venv`, caches, generated bytecode, local IDE state, or temporary output.
- Keep commits focused and messages descriptive.
- Do not rewrite shared history without explicit owner approval.

## 9. Decision discipline

Record consequential or hard-to-reverse choices in `DECISIONS.md`, including context, decision, consequences, and status. Supersede old decisions; do not silently rewrite history.

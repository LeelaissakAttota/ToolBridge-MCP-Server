# Git Workflow
> v1.0.0 release preparation is uncommitted and unpushed until owner approval.

## v1.0.0 release procedure

Before creating release state:

```powershell
python -m pip check
python -m ruff format --check toolbridge tests scripts
python -m ruff check toolbridge tests scripts
python -m pytest tests
docker compose config --quiet
python scripts/verify_release.py
git diff --check
git status --short
```

After explicit owner approval, the suggested commit and annotated tag are:

```powershell
git add .
git commit -m "chore(release): prepare ToolBridge v1.0.0"
git tag -a v1.0.0 -m "ToolBridge MCP Server v1.0.0"
```

Push the branch and tag only with separate owner authorization. Never retag or rewrite a published release tag; correct it with a new semantic version.

## Current repository state

The repository is initialized on the `main` branch and has no commits yet. The project owner should review the foundation and documentation before creating the initial commit.

## Branch policy

- `main` is the stable integration branch.
- Keep `main` runnable and testable.
- Use short-lived branches for approved work.
- Suggested names:
  - `feature/tool-registry`
  - `fix/mcp-lifecycle`
  - `docs/phase-2-plan`
  - `chore/dependency-upgrade`
- Do not begin a phase branch before its scope is approved.

For solo local work, a direct commit to `main` may be acceptable for the initial reviewed baseline. Once the repository is shared, use reviewed merge requests or pull requests.

## Before starting work

1. Confirm the task is approved and listed in `TASKS.md`.
2. Update local `main` without rewriting history.
3. Create a focused branch.
4. Review `PROJECT_RULES.md`, relevant decisions, and security requirements.
5. Define acceptance criteria and required tests.

## Commit rules

- Keep each commit focused and independently understandable.
- Use imperative, descriptive subjects no longer than practical review tools allow.
- Prefer Conventional Commit prefixes:
  - `feat:` new behavior
  - `fix:` defect correction
  - `docs:` documentation only
  - `test:` tests only
  - `refactor:` behavior-preserving restructuring
  - `chore:` maintenance or tooling
  - `security:` security hardening
- Explain why in the commit body when the reason is not obvious.
- Reference the task or decision when useful.
- Never commit secrets, `.env`, `.venv`, caches, generated bytecode, or temporary logs.

Suggested initial commit after owner approval:

```text
chore: establish ToolBridge project foundation
```

## Review requirements

A change is ready for review when:

- Scope and acceptance criteria are clear.
- Tests pass locally.
- New behavior has appropriate tests.
- `python -m pip check` passes after dependency changes.
- Documentation and changelog entries are updated.
- Security implications and secret handling are addressed.
- The diff contains no unrelated formatting or generated files.

Reviewers should focus on correctness, interface stability, failure behavior, security, test quality, and operational impact—not personal style preferences already settled by project standards.

## Merge policy

- Prefer squash merge for a noisy development branch; preserve individual commits when they form a meaningful, reviewable sequence.
- Delete merged short-lived branches.
- Do not force-push `main` or rewrite shared history.
- Do not merge with failing required checks.
- Tag formal releases only after changelog and deployment verification.

## Releases

1. Confirm the intended version and scope.
2. Ensure tests, dependency checks, and deployment smoke tests pass.
3. Move relevant changelog entries from `Unreleased` to the release version and date.
4. Update `toolbridge.__version__` in the same release change.
5. Merge the reviewed release change.
6. Create an annotated Git tag such as `v0.2.0`.
7. Publish artifacts only through the approved deployment workflow.

No remote repository, protected-branch policy, CI checks, or release automation is currently configured.

## Emergency fixes

For an urgent production issue, branch from the deployed tag or current stable `main`, make the smallest safe fix, add a regression test, review security impact, and follow normal release verification. Emergency status does not permit committing secrets or skipping auditability.
